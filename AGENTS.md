# MEAMO — инструкции для Codex

## Назначение и границы

MEAMO — B2B-сайт поставщика продукции из Южной Кореи. Путь пользователя: поиск продукции → изучение характеристик/материалов → запрос условий или документов. **Нет** розничных цен, корзины, онлайн-оплаты, сравнения и накопительного оптового заказа.

Цель — **адаптивная вёрстка 11 типов страниц**, переиспользуемые блоки и клиентские состояния, пригодные для будущей интеграции в действующую MODX. Не менять CMS, не добавлять фреймворк, не разрабатывать backend, не трогать production и не придумывать API. Этот документ задаёт правила **для всего проекта**.

## Источники требований

Перед реализацией страницы читать соответствующие материалы:

1. `files/Страницы/` — 11 пар экранов Desktop 1440 / Mobile 375.
2. `files/Состояния/` — меню, слайдеры, фильтры, Grid/List, пагинация, формы, длинный контент, контрольные 768/1024.
3. `files/UI Kit/` + `files/UI Kit/Примечания.txt` — типографика, компоненты и варианты состояний.
4. `files/MEAMO_ТЗ_верстальщику.docx` — **точный порядок секций** и правила приёмки.
5. `files/MEAMO_ТЗ_программисту_MODX.docx` — будущая логика и контракт данных, **не** поручение интегрировать MODX.
6. `files/MEAMO_Проверка_аннотаций.xlsx` — только при необходимости проверки исторических замечаний.
7. `docs/PAGE_MAP.md` — проверенная карта логических секций, элементов и переиспользования, составленная по 22 основным изображениям и ТЗ.
8. Действующие исходники и `docs/PROGRESS.md`.

Приоритет — основные утверждённые макеты и последние принятые решения, затем актуальные состояния, пояснения и UI Kit. Архивные проверки и скрытые элементы не превращать в новые требования. Не возвращать старые «Показать ещё» и «Все категории и бренды». Тексты `[TEMP]`, условные числа, статусы наличия, источники, документы, рейтинг и контакты из примеров не публиковать как факты. Недостающую информацию фиксировать в `PROGRESS.md`, но не удалять предусмотренный для неё блок. **Файла `MEAMO_Открытые_вопросы.md` нет и не будет** — не искать и не создавать.

## Исходный стек и известные особенности

- Статический HTML (`index.html` — каркас), SCSS (`styles/styles.scss`, `_variables.scss`, `_media.scss`, `_mixins.scss`, `_globals.scss`, `_utils.scss`, `_fonts.scss`) и JavaScript (`scripts/main.js` исходно пустой).
- `styles/blocks/`: заготовки `button`, `form`, `header`, `footer`, `slider`, `breadcrumbs`, `pagination`. Последний блок исходно не импортируется в `styles.scss`.
- Уже лежат jQuery, jQuery UI, jQuery Mask, MicroModal, Swiper. Использовать существующий Swiper, если подходит; остальные библиотеки подключать только при реальной необходимости. MicroModal для заявок запрещён.
- Готовые шрифты Bitter и GolosText, иллюстрации, упаковки и SVG — в `fonts/`, `images/`. Скомпилированный CSS — `styles/css/styles.css`; поддерживать его соответствие исходному SCSS.
- В `_globals.scss` есть ошибочные `line-height` с `px` (например, `1.55px`); текущий `fluid-text` не обеспечивает правильную интерполяцию от 375 к 1440 px; часть блоков — пустые заготовки. Исправлять по мере работы без несвязанного рефакторинга.
- Не предполагать наличие npm-сборщика, маршрутов, сервера или установленных MODX-дополнений, которых нет в проекте. Организовать минимально необходимый локальный запуск и переиспользование HTML; не создавать собственный фреймворк. Критичный контент должен быть доступен без исполнения JS.

## Архитектура, БЭМ, чистота кода

- Писать **минимально необходимый** и читаемый код. Без абстракций «на будущее», лишних зависимостей, мёртвого кода, пустых правил и комментариев, пересказывающих очевидное.
- Сначала найти существующий блок, затем расширить его. Общий по смыслу блок — одна реализация, варианты — БЭМ-модификаторы: `.block`, `.block__element`, `.block--modifier`. Не создавать разные классы ради цвета или положения. Но не объединять принципиально разные сущности в гигантский компонент.
- Например, `card--icon`, `card--text`, `card--white`, `card--icon-side`, `card--enum` могут быть вариантами общей информационной карточки, но карточки товара, категории, документа и статьи могут иметь отдельную структуру.
- Общие Header/Footer, поля формы, кнопки, FAQ, сетки, карточки товаров, пагинацию и заголовки секций поддерживать в едином источнике. Учитывать будущую шаблонизацию MODX. Способ повторного использования статического HTML выбирать самый простой **работающий**, решение записать в `PROGRESS.md`.
- Один самостоятельный БЭМ-блок — один SCSS-файл в `styles/blocks/` с подключением в точке входа. Разделять данные, HTML, оформление и поведение. Не дублировать одну логику между страницами.
- Предпочитать семантический HTML и CSS нативным JS-обработчикам. Без новых анимаций, не предусмотренных макетом.

## SCSS, типографика, адаптивность

- Использовать имеющиеся переменные/миксины и дизайн-токены. Не переопределять визуальную систему: Bitter для акцентов, Golos Text для основного текста, цвета/отступы/радиусы по UI Kit.
- **Главный breakpoint — `@include mobile`.** `desktop`, `tablet`, `mobile-s` допустимы лишь при подтверждённой проблеме компоновки. Использовать Grid/Flex, `minmax()`, `clamp()`, `min()`, `max()`, `calc()`, естественный перенос. Не добавлять breakpoint для каждого отступа.
- **Если размер шрифта на ПК и телефоне отличается, обязательно `@include fluid-text(max, min)`. Не писать `font-size` внутри `@include mobile` для этой задачи.** Миксин можно исправить внутри, сохранив сигнатуру, чтобы получить корректную интерполяцию между 1440 и 375 px. При неизменном размере шрифта достаточно статического значения.
- Контейнер: 1440 → контент 1280 + 80 px слева/справа; 375 → контент 327 + 24 px; на 768/1024 ориентир полей 32 px. Перестройка между ними по устойчивости сетки, а не названию устройства.
- Высоты секций — по содержимому. Не обрезать длинные заголовки и CTA. Товарные изображения — обычно `object-fit: contain`, вся упаковка видна; редакционные фото кадрировать по макету. Резервировать размер медиа при загрузке.
- Не скрывать переполнение глобальным `overflow-x: hidden` вместо исправления причины. Локальная горизонтальная подборка со свайпом допустима, глобальный горизонтальный скролл — нет.
- Проверять 1440/1024/768/375, промежуточные ширины, длинный текст; 320 — дополнительный стресс-тест. Масштабирование не должно ломать формы и колонки.

## Сквозное поведение интерфейса

- Header — непрозрачный закреплённый; поиск только **по товарам и брендам каталога**, не по статьям; на 768/1024 компактное меню и поиск второй строкой. Якоря учитывают реальную высоту Header. Мобильное меню доступно клавиатурой. Footer — полный набор ссылок без мобильного accordion; резерв Trustpilot без выдуманного рейтинга.
- Главный слайдер: стрелки переключают по кругу, номера выбирают слайд, на Mobile доступен свайп; **не** автопрокрутка. Hero Labs статичен. FAQ раскрывается по действию; начальный ответ и возможность нескольких открытых вопросов пока неоднозначны — оставить настройку заменяемой.
- Product Card: Desktop резерв названия около 84 px и выровненные CTA, но длинный текст расширяет высоту ряда; Mobile естественная высота, без усечения и трёхстрочного резерва; строку бренда не дублировать. Предусмотреть пустое изображение.
- Каталог 1440: фильтры слева 288 px + gap 32 + выдача справа 960 px, Grid 3 колонки. На меньших ширинах при тесной компоновке фильтр переходит в мобильную панель. Grid/List — два представления **одного** результата.
- Фильтры: «ИЛИ» между значениями одной группы, «И» между группами. На Mobile черновые значения применяются кнопкой; способ закрытия без применения пока не утверждён. Чип снимает один фильтр, «Сбросить» сохраняет поиск. Изменение условий/сортировки возвращает к странице 1; смена Grid/List сохраняет текущие параметры и страницу. Само раскрытие группы не фильтрует.
- Сортировка только «По умолчанию», «По названию А–Я», «По названию Я–А». Цифровая пагинация, состояния start/middle/end; не «Показать ещё». Отличать «нет результатов» от ошибки загрузки. Состояние каталога должно восстанавливаться по URL/Back/Forward после интеграции; не выдумывать утверждённый формат параметров.
- На товаре «Характеристики», «Описание», «Материалы» — якорные **секции**, не вкладки. На Mobile характеристики перед описанием. Не добавлять sticky CTA или неподтверждённое sticky-поведение локальной навигации.
- Документы имеют точную привязку: материал линейки HA не является инструкцией Fine; Exo — другой товар. Отсутствие документа означает запрос, а не фиктивную ссылку на скачивание.
- Экспертный центр: темы, выбранная/длинная тема, пустая/короткая/полная выдача, неполный ряд выровнен влево, цифровая пагинация. Статья: читаемое оглавление, редакционные источники отдельно от коммерческих блоков, адаптивная таблица; без нового progress bar или sticky-оглавления.

## Формы и CTA

- Заявки **без модальных окон**. Два переиспользуемых типа: компактная (главная, товар, Labs, бренд) и полная (сотрудничество, контакты). Поля/ошибки/согласие/загрузка/состояния общие.
- Компактная: имя, единое поле email или телефон, количество и комментарий, вложение, согласие, контекст товара. Полная: имя, email, телефон, компания, страна/город, список продукции, комментарий, вложение, согласие. Обязательность, правила проверки, типы/размеры вложений **ещё не утверждены**. Не вводить демонстрационные лимиты как постоянные.
- «Запросить условия» — прокрутка к подходящей форме на странице или переход по маршруту **из макета** (например, с «О компании» на «Сотрудничество»). «Запросить документы» — к существующей форме с видимым контекстом ID/названия/URL товара, типа запроса и материала. Не создавать третью отдельную анкету; не помещать персональные данные в URL.
- Состояния `idle → sending → success / error`. **Успех только после ответа реального сервера, прямо на месте формы**; никакого успеха по клику, toast или модалок. Если backend отсутствует, предоставить интерфейс подключения/визуальные состояния, но не имитировать принятую заявку.
- При сетевой/серверной ошибке значения сохраняются, остаётся возможность повторить; повторное нажатие во время отправки заблокировано. Нельзя обещать сохранность файлов после перезагрузки без фактической гарантии. Сервер в будущем проверяет стабильный ID товара сам.
- Выезжающая панель предусмотрена **только для мобильных фильтров**, не для заявок.

## Доступность и контроль качества

Один H1, правильная иерархия, `a` для навигации, `button` для действий, связанные `label`, видимый `:focus-visible`, `aria-expanded`/`aria-current` по необходимости, доступные ошибки и статусы. При закрытии панели фокус возвращать к кнопке открытия, поддерживать Escape и `prefers-reduced-motion`. Не вкладывать кликабельный элемент в другой интерактивный элемент.

**Перед каждым этапом** прочитать этот файл, `docs/PAGE_MAP.md` (для нужных страниц), `docs/PROGRESS.md`, нужные исходники и макеты. После этапа обновить `PROGRESS.md`: 11 страниц со статусом `не начата/частично/реализована/проверена`; общие компоненты с путями; важные решения; непроверенные сценарии; конкретные ограничения backend; следующая задача. Это **снимок состояния**, а не длинный журнал. «Реализована» не равно «проверена». Не заявлять пройденный тест без фактического запуска/просмотра.

Проверять компиляцию SCSS, итоговый CSS, пути, JS-консоль, переполнение, клавиатуру и регрессии на ранее сделанных страницах. Отчёт — что изменено, что реально проверено, что осталось неподключённым. Не считать будущую серверную интеграцию выполненной.

## Страницы и обязательная карта реализации

**Полная проверенная последовательность 11 страниц** — в `docs/PAGE_MAP.md`: пункты `01.1–11.1` с визуальными заголовками, предлагаемыми БЭМ-блоками, вложенными элементами, мобильной компоновкой, особым поведением и картой переиспользования.

При реализации использовать карту **как готовую декомпозицию**, не тратить контекст на повторное самостоятельное изобретение и переименование тех же блоков. При этом карту считать каталогом логических узлов, а исходные изображения и UI Kit — источником точных визуальных величин и состояний. Существующие корректные БЭМ-названия не менять только ради совпадения с предложенными.

Не заменять проверку макета слепым копированием карты: в ней нет полного набора пиксельных параметров, состояний и реальных данных. Если картинка и описание расходятся, проверить утверждённую версию, записать расхождение в `docs/PROGRESS.md`, не придумывать решение.
