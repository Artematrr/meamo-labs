# MEAMO — карта страниц, секций и компонентов

**Основа:** просмотрены 22 основных изображения из `files/Страницы/` (11 Desktop 1440 и 11 Mobile 375), сопоставлены с разделом 5 и требованиями к состояниям из `MEAMO_ТЗ_верстальщику.docx`, а также текущим `AGENTS.md`. Это **спецификация состава и переиспользования**, а не пиксельная спецификация: размеры, интервалы, изображения и подробные состояния Codex сверяет с исходным изображением и UI Kit. Имена БЭМ ниже — **предлагаемые имена реализации**, не имена слоёв Figma и не доказательство существования классов в коде.

Всего в карте **76 основных логических пунктов** по 11 страницам плюс **3 вложенных узла каталога** (фильтры, мобильная панель, панель выдачи).

Обозначения: **Н** — новый блок/новая вариация при первом появлении, **П** — переиспользование; `×N` — столько экземпляров **показано в макете**, но **не жёстко зашито** в шаблон. Данные и фактическое количество объектов в будущем приходят из MODX. Строки с `[TEMP]`, демонстрационные статусы, публикации/ссылки, числа, документы и изображения-примеры не считаются подтверждённым коммерческим контентом.

## 0. Общие компоненты — на всех страницах

| Узел | Предлагаемая БЭМ-структура | Содержимое и важные правила |
|---|---|---|
| Шапка | `header`, `header__logo`, `header__nav`, `header__link`, `header__request`, `header__menu-toggle`, `header__mobile-menu` | Логотип; ссылки «Каталог», «MEAMO Labs», «Сотрудничество», «О компании», «Экспертный центр», «Контакты»; CTA «Запросить условия»; двухстрочная схема с поиском. На Mobile: логотип, «Меню», поиск. Меню отдельное управляемое состояние, не отдельная страница. |
| Поиск | `search`, `search__field`, `search__submit` | Поле «Поиск по каталогу: название товара или бренда»; не поиск по статьям. |
| Футер | `footer`, `footer__brand`, `footer__links`, `footer__group`, `footer__contacts`, `footer__request`, `footer__reviews`, `footer__legal` | Фирменный блок; «Каталог», «Компания», «Связь»; нижний CTA; резерв отзывов Trustpilot; юридические ссылки. На Mobile две колонки ссылок, затем контакты и CTA; без аккордеона. Значения контактов и рейтинг сверить с утверждёнными данными. |
| Навигация/поля | `breadcrumbs`, `button`, `form`, `form__field`, `form__error`, `form__upload`, `form__consent`, `form__status` | Общая разметка и состояния по UI Kit. Не вводить отдельную форму для документов; не делать модалки заявок. |
| Подборка/навигация | `product-card`, `products-list`, `article-card`, `document-card`, `pagination`, `faq` | Карточки разных смысловых типов **отдельные**; их экземпляры переиспользуются в разных секциях. |

**Правило именования:** заголовок секции «Материалы о продукции» не порождает новый БЭМ-блок, если уже есть `documents`; «Экспертный центр» как полоса статей использует `expert-center-block`, а как страница с темами и пагинацией — `expert-center-page` (внутри тот же `article-card`). Новые модификаторы допустимы при визуальном отличии, а не для каждой страницы.

## 13. Правила подключения и проверки этой карты

1. **До создания секции** сверить её номер/порядок здесь; смотреть оригинальную пару изображений, чтобы восстановить точную компоновку и размеры. Из текущих изображений нельзя надёжно восстановить все hover/focus/disabled состояния — они в `files/Состояния/` и UI Kit.
2. Для семантически общих элементов сперва искать существующий код. Если предлагаемые имена конфликтуют с уже корректно принятым БЭМ-именем, **сохранять действующее имя** и в `docs/PROGRESS.md` фиксировать соответствие этой карте. Не выполнять массовый rename без причины.
3. Структура `section` и `div` определяется семантикой, **не** каждую строку таблицы превращать в отдельный обособленный HTML `<section>` с H2 (особенно 02.3a–02.3c, 10.3–10.8). Нумерация описывает логические узлы.
4. Для всех страниц сверять Desktop 1440 и Mobile 375; промежуточные 768/1024 по правилам адаптации из ТЗ, а не додумывать отдельные экраны.
5. В `docs/PROGRESS.md` отмечать сделанное по **номерам 01.1–11.1**, но не сохранять туда полную копию карты. Факт вёрстки, факт визуальной проверки и реальная работоспособность — отдельные статусы.
6. Исторические аннотации, пустые заглушки, нестабильные количества и неподтверждённые бизнес-правила не превращать в требования. Если текущая Figma позднее изменится, эту карту обновить **после сверки**, а не автоматически по устным догадкам.
